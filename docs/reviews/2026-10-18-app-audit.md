# PersonalFinance review — October 18, 2026

## Recommendation

Strengthen the transaction data and reporting foundation before building the conversational agent. The existing React/FastAPI/SQLite stack is sufficient; a rewrite or vector database is not needed for the current dataset.

This is a review, not an implementation plan. Product code and financial records were not changed during this audit. Reproductions used synthetic inputs or isolated in-memory databases. Earlier session changes remain in the working tree.

## Evidence collected

- Reviewed CSV/OFX import, deduplication, enrichment, recurring detection, search, reports, filters, frontend state, settings, persistence, and setup instructions.
- Full backend suite: **92 passed, 4 failed**. The failures are three subscription-detector tests and the Chase parser sign test; these also failed before the recent changes.
- `npm run build` fails in Insights.tsx and Reports.tsx on unused imports, Recharts callback types, and implicit-any parameters. A Vite-only bundle and isolated Transactions TypeScript checks passed earlier; those do not make the full build green.
- Current database: **1,779 transactions**; no exact duplicate groups remained after the prior repair.
- Latest recorded transaction dates: Chase **2026-10-15**, Amex **2026-10-16**, Discover **2026-05-16**. These are observed dates, not proof that every statement period is complete.
- **1,396 of 1,779 transactions have no city.** A purchase-focused check excluding common payment descriptions found 1,269 missing cities among 1,649 rows. City labels also contain variants such as `REDWOOD CITY` / `Redwood City` and incomplete values such as `SAN`.
- Every transaction currently has an embedding, but this does not establish that the embeddings reflect the current enrichment.
- **Zero transactions are marked recurring**, despite a separate subscriptions table containing ten entries, two active.

## Highest-priority findings

### 1. Transaction identity can discard real purchases and still duplicate imports — P1

**Evidence:** [CSV identity](../../backend/parsers/csv_parser.py#L37), [transaction schema](../../backend/db/models.py#L8), [OFX ingestion](../../backend/ofx/client.py#L145), [import deduplication](../../backend/sync_service.py#L83).

CSV IDs use only bank, date, description, and amount. The database has no account/card identity. Two legitimate identical purchases on different Chase cards, or repeated identical purchases on the same day, generate the same ID and are collapsed. OFX uses another fingerprint and ignores the bank FITID for identity, although FITID/account information is available in metadata. Import-batch history does not retain filenames, checksums, rejected rows, or account coverage.

The legacy-sign check fixed the 609 observed duplicate imports, but it is a compatibility repair, not a complete identity model. Do not replace IDs blindly: preserve existing references and migrate with an explicit mapping.

**Improve:** introduce accounts/cards, import batches and raw imported rows; prefer account-scoped bank transaction IDs where supplied. For CSVs without reliable IDs, use overlap reconciliation that preserves repeated-row counts and exposes ambiguous matches for review.

**Acceptance:** repeated imports add nothing; the same purchase on two cards survives; two genuine identical same-day charges survive; charges and refunds remain separate; undoing one import does not delete transactions shared by another import.

### 2. Bank sync and CSV import disagree on spending signs — P1

**Evidence:** [OFX amount handling](../../backend/ofx/client.py#L145), [CSV sign conversion](../../backend/parsers/csv_parser.py#L56), [spending selection](../../backend/transaction_filters.py).

A synthetic OFX debit of `-12.00` is stored as **-12**, while the equivalent Chase CSV purchase is stored as **+12**. Spending queries select positive values, so an OFX purchase can be presented as a refund. OFX and CSV also assign different IDs to that same purchase.

**Improve:** one import normalization service with explicit purchase/refund/payment/transfer kinds, original amount/sign, normalized amount, currency and account identity. Route both ingestion methods through it.

**Acceptance:** the same source transaction imported by CSV or OFX has the same meaning, and overlapping methods reconcile rather than duplicate it.

### 3. Imports can silently lose rows or appear successful when they failed — P1

**Evidence:** [parser error handling](../../backend/parsers/csv_parser.py#L47), [upload endpoint](../../backend/routes/import_csv.py#L96), [import service](../../backend/sync_service.py#L83).

A CSV with unrecognized columns currently parses to an empty list without an error. Invalid dates and amounts are silently skipped. `total_parsed` is computed after in-file deduplication, hiding the difference between original rows, rejected rows and collapsed rows. Upload also performs synchronous DB/LLM work inside an async endpoint before returning; this can block the event loop and make client timeouts ambiguous while server work continues.

**Improve:** validate headers and file size, preview import/account/date coverage, report accepted/duplicate/rejected counts with line-level reasons, persist raw rows first, then run enrichment as a separate job. Generate safe internal filenames and retain the original filename as metadata.

**Acceptance:** wrong-bank files fail clearly; malformed rows are visible; transactions can be imported when the LLM is unavailable; a client retry attaches to the same import rather than creating uncertain work.

### 4. Recurring detection can destroy manual state and does not power the recurring filter — P1

**Evidence:** [re-detect endpoint](../../backend/routes/transactions.py#L79), [detector](../../backend/analysis/subscription_detector.py#L21), [import updates](../../backend/sync_service.py#L135), [recurring field](../../backend/db/models.py#L21).

An isolated reproduction confirmed that re-detecting with no detected results deletes a manually created subscription. The endpoint deletes every subscription and recreates detected entries, losing manual additions, dismissals and active-state choices. Routine imports update existing amounts/dates but do not reconcile active flags. The detector requires three transactions before checking frequency, so two annual payments are never considered. No production path sets Transaction.is_subscription, leaving the new recurring filter empty for detected subscriptions.

**Improve:** distinguish manual entries from detected candidates; link recurring series to supporting transactions; preserve user confirmation/dismissal; reconcile detector output rather than replacing the table. Derive the recurring filter from those links. Support annual recurrence with two observations and an appropriate confidence level.

**Acceptance:** manual entries and dismissals survive re-detection; recurring filters return supporting transactions; inactive stale services do not silently remain active; annual subscriptions can be detected within two years of history.

### 5. Report drilldowns do not show the transactions behind the numbers — P1

**Evidence:** [report category link](../../frontend/src/pages/Reports.tsx#L181), [merchant link](../../frontend/src/pages/Reports.tsx#L214), [Transactions URL handling](../../frontend/src/pages/Transactions.tsx#L22).

Reports send `category`, `dateFrom`, `dateTo`, and `search`. Transactions reads only `month`, `merchant`, `q`, and `ids` from the URL; category/date state starts empty. The destination can therefore show unrelated dates/categories or ignore the selected merchant.

**Improve:** define one typed filter contract used by URL serialization, frontend state, API queries and exports. Read and write all active filters in the URL; preserve them through back/forward navigation.

**Acceptance:** a category/merchant total opens the matching period and subset; refreshing or copying the URL preserves the view. This is essential for future agent citations.

### 6. Reports lack account coverage and freshness context — P1 before agent

**Evidence:** [sync schema](../../backend/db/models.py#L36), [overview/report queries](../../backend/routes/analysis.py).

Discover stops in May while Chase/Amex reach October. The app aggregates them without saying that recent totals omit months of Discover activity. A latest transaction date is not proof of complete coverage. City queries have a similar problem: missing or incomplete cities are indistinguishable from genuine nonmatches.

**Improve:** track imported statement periods and account coverage; show stale/missing sources beside totals. Keep unknown locations explicit and separate extracted city, normalized city, and evidence/source. Let the user correct uncertain merchant/location fields.

**Acceptance:** a question about recent spending or all transactions in a city reports the period, included accounts and relevant unknown/missing data rather than implying completeness.

## Important reliability and analysis findings

### 7. AI output and user corrections need provenance — P2

[Enrichment/reclassification](../../backend/routes/import_csv.py#L141) has only a process-local status dictionary/lock. Reloading the server loses job state; duplicate requests can overwrite status with pending; processed counts include fallback rows. Valid `other` classifications and failed enrichment share the same retry selection. Re-categorize always overwrites categories, including manual corrections, because there is no manual-override marker. Fuzzy merchant normalization rewrites names in place without a persistent alias/evidence record.

Persist job IDs, attempts, per-row outcomes, model/prompt versions, input hashes, and error reasons. Separate bank data, AI proposals and user overrides. Add a small review queue for uncertain fields. Use explicit merchant aliases with reversible merges rather than relying solely on global fuzzy rewrites. Keep valid results when other rows fail.

### 8. Cached narratives and embeddings can contradict current data — P2

[Monthly narrative cache](../../backend/routes/analysis.py#L162) is keyed only by year/month. Standard import, category edits, enrichment and subscription changes do not invalidate it. The duplicate repair manually invalidated affected months, but there is no general mechanism.

[Embedding text](../../backend/search/embedder.py#L27) omits enriched merchant, city and merchant type. A reproduction confirmed changing merchant/city leaves the embedding text unchanged. [Embedding generation](../../backend/routes/search.py#L106) only selects missing embeddings; category edits do not mark existing embeddings stale. Imports do not explicitly schedule indexing after enrichment.

Use data revisions/input hashes for derived artifacts, include the intended enriched fields, and rebuild only affected records after successful updates. Return actual readiness/freshness rather than implying that an incomplete index is still actively processing.

### 9. Average and refund semantics are inconsistent — P2

[Monthly averages](../../backend/analysis/insights.py#L279) excludes the current calendar month but counts other months whenever at least one selected transaction exists. A January 15–31 range is counted as one complete month. Months without rows are absent from the denominator; the app cannot distinguish zero spend from missing imports. [Category summaries](../../backend/routes/analysis.py#L49) instead divide by `days / 30`, so similarly labeled monthly averages can disagree.

Most reports exclude every negative record, displaying gross purchases rather than net spending after refunds. That can be a valid metric, but it needs a clear label and consistent alternatives.

Define complete-calendar-month, rolling-period, gross purchases, refunds, and net spending once. Calculate averages using covered periods; mark partial or unobserved periods explicitly. Store money as integer minor units (or exact decimals with currency) rather than binary floats as the model evolves.

### 10. Build, setup and tests are not a dependable baseline — P2

The full TypeScript build fails. Backend tests contain stale sign expectations, and the annual detector failure also exposes the real two-observation limitation. [README setup](../../README.md#L39) points to root requirements.txt, which is absent; the actual file is backend/requirements.txt. That file does not explicitly declare sentence-transformers although application startup imports it. Existing runtime dependencies differ from the old pinned setup file.

Restore a green build/test baseline, document a supported Python version and working start commands, declare direct dependencies and use a reproducible backend lock/environment. Add boundary tests for raw import reconciliation, job recovery, report links, manual overrides and cache/index invalidation. A lightweight CI check should run these on every change.

## UX and architecture improvements after the above

- **One consistent interface:** Reports uses a dark content palette while the app main canvas is light, including a white page heading. Use shared typography, controls and spacing, a responsive sidebar/table layout, accessible sort/filter controls, and consistent loading/error/retry states. This visual finding comes from source inspection; live screenshot validation was interrupted by user browser activity.
- **More useful overview:** show data freshness, import/enrichment health, a clearly labeled gross/net metric and a route to the rows that need attention. Import controls currently dominate the overview.
- **Correction workflow:** allow merchant/city corrections and reusable rules, not just one-row categories. Show which fields come from the bank, AI, or a manual edit.
- **Shared transaction service:** payment keywords and spending decisions are repeated across routes, jobs and analyses. Centralize selection, classification and aggregation rules so charts, exports and the future agent agree. Reuse the recently added shared filter query as a starting point.
- **Scale proportionately:** the database currently has only its primary-key index; several routes load every transaction and the UI renders all rows. Add ordinary indexes and pagination as needed. Keep search's 50-result ranking distinct from exhaustive lookup and full-set aggregation. No vector database is required at this size.
- **Agent boundary:** expose bounded, read-only lookup/aggregation tools with validated filters and source transaction IDs. Return counts, sums, date/account coverage and unknown-field counts. Let the database calculate totals and let the LLM explain them. Keep financial descriptions as untrusted data rather than tool instructions.

## Suggested delivery order

1. **Reliable records:** account/import provenance, common sign/type semantics, CSV validation and reconciliation. Preserve existing data via backed-up migrations.
2. **Correct product behavior:** recurring-state preservation/links, URL drilldowns, cache invalidation, calendar/refund semantics, freshness/quality indicators.
3. **Operational baseline:** green full build/tests, persistent resumable enrichment, safe manual overrides, dependency/setup cleanup and focused UI polish. Build/test fixes can begin alongside phase 1.
4. **Question answering:** exhaustive lookup, grouped aggregation and merchant/city resolution tools; then the chat interface with evidence links and coverage context.

Before accepting the agent, test questions against known fixtures: merchant aliases, incomplete city data, stale accounts, refunds, two identical real purchases, multiple cards, missing months, and questions requiring more than 50 rows. Compare every count and total against database results.
